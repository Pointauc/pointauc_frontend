# Spin Tickets — Frontend Integration Guide

This document explains how the frontend should interact with the spin tickets API. It describes the user flow, the idea behind each endpoint, and the order in which endpoints are called. It intentionally does **not** duplicate request/response schemas — the exact data structures live in the generated API client (produced by the API generation and sync command from `openapi-docs/client-api.json`).

## What this feature is for

The spin tickets system makes winner selection on the wheel verifiable. Before a spin, the streamer's account holds exactly one **active ticket** — an invisible commitment to a random number in `[0, 1)`. When the wheel starts, the ticket is **revealed**: the participants list is permanently bound to it, the number becomes known, and the winner is calculated. Anyone can later re-do the calculation from the published data and confirm the spin was fair.

Two verification providers back the tickets:

- **`random-org`** — the number is generated by Random.org at reveal time, and the response carries their signed data and signature under `verificationMetadata` so anyone can verify it against Random.org independently.
- **`backend`** — the backend generated the number itself (used when the Random.org daily quota is exhausted or the API is unavailable, so the feature never blocks the streamer). For these tickets `verificationMetadata` is `null`.

Which provider was used is exposed in the revealed ticket data; the UI can badge spins as "Random.org verified" or "backend verified".

## The two UI contexts

1. **Streamer wheel UI** — authenticated (session cookie), one browser, drives the lifecycle.
2. **Verification page** — anonymous, public, at `{host}/spin-verification/{ticketId}`. Viewers open it from a link the streamer shares (the ticket ID is a short alphanumeric code like `k7f2mq9w3p`).

## Lifecycle and endpoint call order

### 1. `GET /random/tickets/active` — streamer UI, on load (and whenever a fresh ticket is needed)

Returns the account's active ticket. **There is no create-ticket endpoint**: if the account has no active ticket, this call creates one and returns it. Call it when the wheel page opens; the response is what you show while waiting for the user to press start.

Key properties of the active ticket:

- The account can have only **one** active ticket at a time.
- It **cannot be discarded or reset** — there is no delete endpoint, by design. The commitment only completes when the ticket is revealed.
- The response includes `quotaLeft` (how many Random.org-backed tickets remain today). It's informational; the fallback to the backend provider is automatic and needs no UI handling.

### 2. `POST /random/tickets/reveal` — streamer UI, when the user clicks start and the wheel begins spinning

Sends the auction participants list. This:

- binds the list to the ticket,
- generates/produces the random number,
- calculates the winner,
- returns the **full result to the streamer immediately** — use it to run the wheel animation and show the winner locally,
- automatically creates the next active ticket (so step 1's response becomes stale; call `GET .../active` again before the next spin),
- **keeps the result hidden from the public** — the response's `isRevealedForViewers` is `false` at this point.

The spin is now "in progress" and the verification page shows a spin-in-progress state (see the state matrix below).

### 3. `POST /random/tickets/{ticketId}/reveal-for-viewers` — streamer UI, when the spin animation ends

Publishes the result of that specific ticket: from this moment the verification page and the revealed-tickets list show the full data to everyone. Call it exactly once per spin, when the wheel stops and the winner has been presented locally. It is idempotent — if the request is retried or duplicated, the state simply stays published.

Only the ticket owner can publish it; it must already be revealed (calling it before the reveal fails).

### 4. `GET /random/tickets/{ticketId}` — verification page, poll this

Public, anonymous. The response's `revealed` and `isRevealedForViewers` flags are **always present** — build the page as a state machine on them:

| State | `revealed` | `isRevealedForViewers` | What the page should show |
|---|---|---|---|
| Waiting | `false` | `false` | Ticket exists, nothing has happened yet ("waiting for spin") |
| Spin in progress | `true` | `false` | The wheel is spinning. Anonymous visitors and other accounts get only minimal data (plus the reveal timestamp) — no number, no participants, no winner. **Exception:** if the visitor is authenticated as the ticket owner, the full result is returned, so the streamer can preview their own spin. |
| Published | `true` | `true` | The complete result: random number, bound participants, winner, verification metadata. Anyone can verify it. |

The intended anti-spoiler behavior: a viewer who opens the verification page while the wheel is still spinning must not be able to see who won before the streamer's animation reveals it. The backend enforces this; the page just renders whichever state it receives. Polling this endpoint is the way the page transitions between states.

### 5. `GET /random/tickets/revealed?userId=...` — archive pages

Public, paginated list of a user's spins whose results are visible to viewers (in-progress spins are excluded). Returns only short summaries — ticket ID, winner metadata, reveal timestamp — suitable for "recent spins" lists that link to the verification page.

## Error handling notes

- Streamer endpoints require the session cookie; without it they respond `403`.
- `POST .../reveal` returns `NO_ACTIVE_TICKET` if there is no active ticket — recover by calling `GET .../active` first.
- `TICKET_HAS_BEEN_USED` (rare, `422`) means Random.org refused the reveal; the ticket is **not consumed**, the user can retry the spin.
- `reveal-for-viewers` returns `TICKET_NOT_REVEALED` if called before the reveal, and `404` for unknown ticket IDs or tickets belonging to another account.
- `GET /random/tickets/{ticketId}` returns `404` for an unknown ticket ID.

## Things that intentionally do not exist

- No create-ticket endpoint — creation is implicit in `GET .../active`.
- No delete/reset/discard endpoint — a ticket can only be completed by revealing it.
- No endpoint that exposes the Random.org ticket ID or any other internal identifier; the short ticket ID is the only public identifier.
